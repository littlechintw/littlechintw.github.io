[音樂祭行程](https://mf.littlechin.tw/) 是我從 2025 年底開始做的 side project：一個純前端的 PWA（Progressive Web App），可以瀏覽各音樂祭的時間表、把想看的演出排成自己的行程、在演出前收到提醒，而且現場沒網路也能查。這篇想記錄為什麼要做它、幾個關鍵的設計決定，以及整個專案幾乎都靠 AI 寫出來的心得。程式碼在 [GitHub](https://github.com/littlechintw/Music-Festival-Timeline) 上。

## 為什麼要做

2024 年的時候，我看到朋友為了大港開唱做了一個 timeline 網頁，把各舞台的演出排成一條時間軸。我覺得這個想法很棒，一直想自己做一個，但始終沒有時間。直到 AI 寫程式的能力越來越強，我想說或許可以靠它把這件事做起來，於是在 2025 年 11 月開了這個專案，第一場放進去的資料是當年的火球祭。

參加過幾次音樂祭之後，我發現有一個痛點大家都遇過，卻很少有工具認真處理：人一多，現場的網路就會塞到不能用。這時候想查下一場在哪個舞台、幾點開始，官方網站或 IG 根本打不開。所以「離線可用」從一開始就是這個專案的核心需求，而不是附加功能。

另外，台灣一年有非常多場音樂祭，我不希望這只是為了某一場做的一次性網頁。所以我定義了一個 JSON 的資料格式，一場音樂祭就是一個檔案，任何人都可以照格式新增或修正時間表，再用 PR 送進來。

## 離線是怎麼做的

整個網站是用 Vue 3 加上 Vite 做的 PWA，部署在 GitHub Pages。離線的部分靠 Service Worker，但「哪些資料要存在手機裡」我花了比較多時間想，最後定了三條規則：

1. 近期活動自動下載：開始前 30 天到結束後 14 天的音樂祭，打開 App 時就會下載到裝置並一直保留。
2. 其他活動點開才下載：列表只靠一份很小的索引就能顯示所有音樂祭，點進詳情或時間軸時才抓完整的時間表。
3. 30 天沒用就移除：每場活動記錄最後使用時間，超過 30 天沒打開就從裝置移除，期間有打開就重新計算。

索引裡帶著每份 JSON 的 hash，App 比對本機的 hash 一樣就完全不打網路。有新版本的時候畫面會提示「有新版本可用」，使用者按下才切換，不會打斷正在看的畫面。場地地圖可以直接以 base64 塞進 JSON 裡，所以離線時一樣看得到。

*設定頁可以看到哪些資料存在手機裡；新增音樂祭的編輯器附了一段 Prompt，讓 AI 幫你把時間表圖片轉成 JSON*

## 不花錢的分享功能

我希望這個專案不要有任何伺服器成本，所以整個網站只有純前端。唯一需要後端的是「分享行程給朋友」，這部分我用之前做的 [短網址服務](https://github.com/littlechintw/Short-Text-Tool) 去包裝：後端是一支 Google Apps Script，資料存在 Google Sheet，API 只有「建立」和「查詢」兩個動作，完全不用租伺服器。

行程本身會先壓成一行純文字，只記音樂祭 ID、舞台名稱與每場的開始時間，接收端再用自己裝置上的時間表還原完整資訊：

```text
wind-top-fest-2026;風神舞台:06271200,06271340;雷神舞台:06271100
```

這段文字交給短網址服務換成一個三碼的短碼，朋友點開連結就能匯入。後來也加了 QR Code 的離線分享：同一段文字直接轉成 QR Code，雙方都不需要網路，很適合在現場互相交換行程。

![左邊是分享行程的對話框，可以選雲端短網址或離線 QR Code；右邊是產生好的 QR Code](/images/blog/music-festival-web-app/03-share.png)

*分享有雲端與離線兩種方式，現場沒網路就用 QR Code*

## 時間軸與行程

![左邊是大港開唱的全日時間軸，多舞台甘特圖；右邊是我的行程，重疊的演出會標示時間衝突](/images/blog/music-festival-web-app/02-timeline-and-plan.png)

*全日時間軸是多舞台的甘特圖；我的行程會把跨舞台撞時間的演出標出來*

時間軸是以 5 分鐘為一格的多舞台甘特圖，當天會有一條紅色的「現在」線並自動捲到當下。我的行程可以跨音樂祭、跨日，兩場演出時間重疊會直接標示衝突，也能匯出成圖片或 .ics 加進行事曆。演出前幾分鐘要提醒可以自己設定，透過 Service Worker 推播，分頁沒開著也會跳。行程累積久了，「聽過的藝人」頁面還會幫你統計看過哪些藝人、看了幾次。

![場地地圖頁面，顯示大港開唱 2026 的場地配置圖，下方標示地圖已存在裝置上](/images/blog/music-festival-web-app/04-map.jpg)

*場地地圖也會存在裝置上，離線一樣能看*

## Vibe Coding 的體會

老實說，這個專案絕大部分的程式碼都是 AI 寫的。從一開始很糟糕的 UI，到現在比較能看的樣子，中間經歷了好幾輪重寫，有幾個功能甚至是直接請 GitHub Copilot 的 coding agent 開 PR 完成的。

對 Vibe Coding 這件事，我心裡其實一直有一點疙瘩，大概是因為看到很多沒有工程背景的人也在用，會懷疑這樣做出來的東西到底穩不穩。但實際做下來，我覺得之前寫過不少前後端的經驗還是很關鍵：知道 Service Worker 的 precache 跟 runtime cache 差在哪、知道 CORS preflight 為什麼要避開、知道資料格式要用 schema 驗證，這些讓我可以很快判斷 AI 給的方案對不對，遇到問題也能自己定位，而不是一直重新 prompt。

UI 是比較後期才改的。前期我只是籠統地叫 AI「做好看一點」，效果很有限；後來改成請它完全照 Google 的 Material Design 3 來做，用它的色票、元件與間距規範，整個品質一下子提升很多。有一套設計師定好的 Design System 給 AI 當依據，比自己憑感覺描述有效得多。

![深色模式下的音樂祭列表與全日時間軸](/images/blog/music-festival-web-app/06-dark-mode.png)

*改用 Material Design 3 之後，深色模式也是順便就有了*

## 結果與下一步

到目前為止專案裡已經有 11 場音樂祭的時間表，從 2025 年的火球祭到 2026 年的大港開唱、風神祭、Jam Jam Asia 等。最近看到有人 fork 了這個專案，也看到有人真的在用，蠻開心的。雖然還有很多可以改進的地方，但至少證明了這個東西是有價值的。

接下來希望能持續更新資料，也希望有更多人一起維護，像是直接用編輯器裡的 Prompt 讓 AI 讀時間表圖片，產生 JSON 之後送 PR。如果你也常跑音樂祭，歡迎試試 [mf.littlechin.tw](https://mf.littlechin.tw/)，有遇到問題或想新增哪一場，都可以到 [GitHub](https://github.com/littlechintw/Music-Festival-Timeline) 開 issue。
