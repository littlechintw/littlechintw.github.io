# 文章寫作規範

這份文件說明文章要放哪裡、frontmatter 怎麼填、內文怎麼寫，以及送 AdSense 審核時要避開的地雷。
寫新文章最快的方式是：

```bash
npm run new -- "文章標題" my-post-slug --tags 開發,工具
npm run dev        # http://localhost:4321 預覽，草稿也看得到
```

寫完把 `draft: true` 改成 `false`，推上 `main` 就會自動部署。

## 檔案放哪裡

```
src/content/blog/
├── _template.md                 # 範本（底線開頭，不會被收錄）
├── taiwan-toilet-map-data.md    # 一篇文章 = 一個 .md
└── ...
public/images/blog/
└── taiwan-toilet-map-data/      # 這篇文章的圖片，資料夾名稱 = slug
    ├── 01.jpg
    └── cover.jpg
```

- **檔名就是網址**：`taiwan-toilet-map-data.md` 會變成 `https://littlechin.tw/blog/taiwan-toilet-map-data/`。
- slug 只用小寫英文、數字和連字號，不放日期、不放中文。短、好懂、以後不會想改。
  - 好：`toilet-map-open-data-pipeline`、`hitcon-2025-photo-notes`
  - 不好：`2026-10-20-文章`、`post1`、`My_New_Post`
- 系列文在 slug 結尾加序號：`pdis-ray5-internship-1`、`-2`、`-3`。
- 圖片放在 `public/images/blog/<slug>/`，在文章裡用絕對路徑引用：`![說明](/images/blog/<slug>/01.jpg)`。
- 發佈後不要改 slug。真的要改，舊網址會變 404。

## Frontmatter 欄位

欄位由 `src/content.config.ts` 驗證，填錯會在 `npm run dev` 或 `npm run build` 時直接報錯並告訴你哪裡錯。

```yaml
---
title: "廁所地圖的資料是怎麼來的"            # 必填，80 字內
description: "從環境部開放資料到地圖上的每一個點：抓取、清理、分縣市切檔與每週自動更新的流程。"  # 必填，20～160 字
pubDate: 2026-10-20                          # 必填，YYYY-MM-DD
updatedDate: 2026-11-02                      # 選填，有大幅修改時再填
tags: [開發, 工具, 開放資料]                  # 選填，最多 6 個
cover: /images/blog/taiwan-toilet-map-data/cover.jpg   # 選填，文章頁最上方與分享預覽用
coverAlt: "廁所地圖在手機上的畫面"             # 有 cover 就填
draft: false                                 # true = 只在本機預覽，正式站不輸出
lang: zh-TW                                  # 預設 zh-TW，英文文章填 en
source:                                      # 轉載／原發表於其他平台才填
  name: Medium
  url: https://medium.com/@littlechintw/...
---
```

| 欄位 | 必填 | 說明 |
| --- | --- | --- |
| `title` | 是 | 文章標題。具體、有資訊量，讓人一眼知道這篇在講什麼。避免「心得」「雜記」這種看不出內容的標題。 |
| `description` | 是 | 一到兩句摘要，會出現在文章列表、首頁、搜尋結果與社群分享卡片。寫「這篇解決了什麼」而不是「這篇是關於什麼」。 |
| `pubDate` | 是 | 發佈日期。轉載的文章填原本的發佈日期。 |
| `updatedDate` | 否 | 內容有實質更新時填寫，文章頁會顯示「更新於」。錯字修正不用填。 |
| `tags` | 否 | 標籤，用來分類與產生 `/blog/tag/<標籤>/` 頁面。不能含空白或 `/ # ?`。 |
| `cover` / `coverAlt` | 否 | 封面圖。建議 1200×630 以上，JPG 控制在 300 KB 內。 |
| `draft` | 否 | 草稿。預設 `false`。 |
| `lang` | 否 | 文章語言，影響 HTML 的 `lang` 屬性與排版。 |
| `source` | 否 | 原發表平台。文章底部會顯示「本文原發表於 …」。 |

### 標籤怎麼取

標籤少而一致比多而雜好。優先從這個清單選，真的沒有再新增：

- 主題：`開發`、`資安`、`攝影`、`社群`、`工具`、`職涯`、`實習`、`旅行`、`UX`
- 專有名詞直接用原名：`PDIS`、`HITCON`、`SITCON`、`COSCUP`、`GDSC`、`NTPU`、`TNFSH`
- 專案名用中文：`廁所地圖`、`音樂祭行程規劃`、`短網址服務`

一篇文章兩到四個標籤最剛好。

## 內文怎麼寫

### 長度與結構

- **正文至少 800 字，目標 1,200 到 2,000 字。** 這是 AdSense 審核與搜尋引擎判斷「有沒有實質內容」的門檻，也是讀者願意讀完的長度。
- 開頭一段講清楚：這篇要解決什麼問題、誰會需要、讀完會得到什麼。不要從「大家好，好久沒寫文章了」開始。
- 用 `##` 分段，每段一個重點。標題從 `##` 開始，不要用 `#`（那是文章標題）。`###` 給小節，不要再更深。
- 結尾收一段：做了什麼、學到什麼、下一步。有相關文章就在這裡連過去。
- 條列用 `-`，步驟用 `1.`。表格可以用，但手機上寬表格不好讀，欄位控制在三到四欄。

### 寫作方式

- 寫你自己做過、遇到、想通的事。你的經驗是別人搜不到的，官方文件已經有的內容不用重抄。
- 具體勝過抽象：「資料裡有 1,300 多筆重複的廁所，判斷方式是名稱加座標距離小於 30 公尺」比「資料有一些重複要處理」有用得多。
- 有程式碼就放程式碼區塊並標語言，方便上色：

  ````markdown
  ```js
  const nearby = toilets.filter((t) => distance(t, here) < 500)
  ```
  ````

- 專有名詞第一次出現時給全名或一句解釋，例如「SUS 量表（System Usability Scale）」。
- 中英文之間空一格，數字與單位之間空一格：「花了 3 天」、「使用 Vue 3」。
- 站內文章用相對路徑連結：`[上一篇](/blog/pdis-ray5-internship-1/)`。站外連結用完整網址。

### 圖片

- 每張圖都要有 alt 文字，描述圖裡有什麼，不要留空或只寫「圖片」。
- 圖片下一行用斜體寫圖說，網站會把它排成置中的小字：

  ```markdown
  ![成果發表當天的攤位](/images/blog/pdis-ray5-internship-4/01.jpeg)

  *成果發表當天的攤位*
  ```

- 檔案用 JPG（照片）或 PNG（截圖），寬度 1600px 以內，單張 300 KB 以下。截圖記得遮掉個資與 token。
- 只放自己拍、自己截的圖。別人的圖要有授權並註明出處。

## AdSense 與搜尋引擎會在意的事

這些不是寫作技巧，是審核會直接退件的原因：

1. **原創**。不要整段貼別人的文章、官方文件或 AI 產生的泛泛內容。引用請用 `>` 並附來源，引用的量要遠少於自己寫的量。
2. **沒有施工中的痕跡**。不要發佈只有標題和兩行字的文章，不要留「待補」「TODO」「Coming soon」。還沒寫完就維持 `draft: true`。
3. **不放敏感資訊**。攻防演練、滲透測試、客戶或公司內部的細節，只寫可以公開的部分。不確定就不寫。
4. **不要為了湊字數寫**。十篇 1,500 字的真實經驗，比三十篇 300 字的流水帳有用。
5. **每篇文章都要能獨立被讀懂**。從搜尋引擎進來的人沒看過前一篇。

## 發佈前檢查

- [ ] `description` 寫好了，不是範本預設文字
- [ ] `pubDate` 正確，`draft: false`
- [ ] 正文 800 字以上，有 `##` 分段
- [ ] 所有圖片都在 `public/images/blog/<slug>/`，都有 alt
- [ ] 程式碼區塊有標語言
- [ ] 站內連結用 `/blog/.../` 格式，點得到
- [ ] `npm run build` 沒有錯誤
- [ ] 手機寬度看過一次

## 轉載舊文章

從 Medium 或其他平台搬文章過來時：

1. `pubDate` 用原本的發佈日期。
2. 加上 `source`，文章底部會自動標示出處。
3. 圖片下載到 `public/images/blog/<slug>/`，不要連回原平台的圖床。
4. 原文裡指向其他舊文章的連結，改成站內路徑。
5. 可以趁機修錯字與排版，但不要大改內容；想補充就另外寫一篇新的。
